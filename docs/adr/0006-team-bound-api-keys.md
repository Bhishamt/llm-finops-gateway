# 0006. Team-bound API keys; headers only narrow, never override

Date: 2026-11-15
Status: Accepted (supersedes the "trusted headers" assumption in ADR-0003)

## Context

ADR-0003 made `X-Team` mandatory but trusted it as declared. That is fine on a laptop and
useless in production: any caller can charge another team, and budgets become advisory. The
attribution dimension has to come from something the caller cannot forge.

Options considered:

1. **Gateway-issued keys bound to a team.** Same shape as an OpenAI key, so every SDK already
   sends it (`Authorization: Bearer`). No identity provider needed.
2. **JWT / OIDC claims (Entra ID).** Strongest, but requires an IdP integration and a claim
   mapping per customer, and most LLM client code has no token acquisition path.
3. **mTLS or network identity.** Infrastructure-specific; attribution would live outside the
   repo.

## Decision

Option 1 now, option 2 later behind the same `Attribution` value object.

- A key identifies a **team**, optionally restricted to a list of projects, with an optional
  expiry and a disabled flag. It is labelled with an `id` that appears in the ledger
  (`key_id`), the response and the traces, so a leaked key can be traced and rotated without
  guessing.
- The gateway stores **only SHA-256 hashes** in `config/keys.yaml`, which can therefore live in
  git next to prices and policies. Raw keys are generated by
  `llm-finops-gateway keys new --team <team> --id <label>`, printed once, and handed to the
  team's secret store. Lookup is a constant-time hash comparison.
- `LFG_AUTH_MODE=api_key` is the default. In this mode `Authorization` is required (401
  otherwise), the team is taken from the key, and `X-Team`, if sent, must match (403
  `team_mismatch`). `X-Project` remains required and may be restricted by the key (403
  `project_not_allowed`).
- `LFG_AUTH_MODE=headers` keeps the ADR-0003 behaviour for development and for networks where
  an upstream proxy already authenticates callers. The gateway logs a warning at startup.
- Missing key file in `api_key` mode is a startup error, not an empty ring, so a misconfigured
  deployment fails loudly instead of returning 401 to everyone.

## Consequences

- Clients set `api_key` to the team key and `default_headers={"X-Project": ...}`; nothing
  else changes.
- Keys are per team, not per person. Per-person attribution (and per-person budgets) needs
  the JWT path and a decision about privacy; out of scope here.
- Rotation is: generate a new key, add its hash, deploy, switch the client, mark the old one
  `disabled: true`, deploy. Two entries for one team are expected during rotation.
- The key file is config, so a leaked repository leaks hashes only. A leaked *raw* key is
  bounded by the team's budget and allow-list, which is the point of having them.
